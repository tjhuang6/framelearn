# 提案：自然语言命令解析器

## 问题

FrameLearn 目前采用传统 CLI 命令格式（`framelearn run <URL>`、`framelearn ask <问题>`），用户需要：
- 记住命令关键词（`run` / `ask` / `summarize`）
- 理解参数格式（URL 必须用引号、问题要完整拼写）
- 切换不同功能时记住不同命令

这不符合"AI Agent"的定位——用户应该能用自然语言描述需求，Agent 理解后执行。

---

## 提议方案

在整个系统最外层加一个 **CommandParser** 模块，作为自然语言入口：

```
用户输入：
  "帮我把这个视频转成文档 https://..."
  "第 3 章讲了什么"
  "总结一下我学到的"

     ↓

CommandParser（LLM 意图识别）

     ↓

标准命令：
  run https://...
  ask 第 3 章讲了什么
  summarize

     ↓

CommandRouter 路由执行
```

---

## 为什么现在做

这是整个系统的**入口层**，决定了用户体验的第一印象。

如果等主流程（视频处理）都写完再加，会面临：
- CLI 入口（`__main__.py`）已经写死了命令解析逻辑
- 用户习惯了传统命令，再改会破坏兼容性
- 测试代码、文档示例都要重写

**现在做**的好处：
- 主流程还没写，CLI 入口还是空的，加这一层零成本
- 从一开始就建立正确的交互模式
- 向后兼容：传统命令（`run` / `ask`）跳过 LLM 解析，直接执行

---

## 价值

### 用户体验提升

```
旧：framelearn run "https://bilibili.com/video/BV1xx..."
    ↑ 需要记住 run 关键词，URL 要加引号

新：framelearn "帮我处理这个视频 https://..."
    ↑ 自然语言，无需记忆格式
```

### 符合 Agent 定位

FrameLearn 的核心是 Agent（ReAct 循环、自主决策），但入口却是传统 CLI——用户感知不到"Agent"的存在。

加了自然语言解析后，用户的第一印象就是"这是一个理解我说话的 AI"，而不是"又一个命令行工具"。

### 扩展性

未来可以加：
- 多轮对话："处理这个视频" → "哪个视频？" → "https://..."
- 上下文记忆：用户说"继续"，Agent 知道继续什么
- 语音输入：接入 Whisper，口述命令

这些都基于 CommandParser 这一层。

---

## 成本

### 开发成本

- **CommandParser**：约 100 行（LLM 调用 + Prompt）
- **CommandRouter**：约 150 行（路由逻辑）
- **测试**：约 50 行（意图识别准确性测试）

总计：~300 行代码，1-2 天工作量。

### 运行成本

每次解析调用 LLM：
```
使用 DeepSeek（推荐）：
  输入：~500 tokens（System Prompt + 用户输入）
  输出：~10 tokens（命令）
  成本：$0.00007 / 次

100 次调用成本：$0.007（可忽略）
```

对比视频处理的成本（$0.20-4.00 / 视频），这个开销完全可以忽略。

### 延迟

LLM 解析耗时：~200-500ms（DeepSeek / Gemini Flash）

对于视频处理（耗时几分钟到几小时）和问答（用户可以等），这个延迟用户感知不到。

---

## 风险与对策

### 风险 1：LLM 解析错误

```
用户输入："处理这个视频"（没给 URL）
LLM 错误输出：run（缺少参数）
```

**对策**：
- Prompt 里明确要求：缺少 URL 时输出 `error: 缺少视频链接`
- Router 执行前验证参数完整性
- 解析失败时提示用户用传统命令格式

### 风险 2：意图识别不准

```
用户输入："这个视频讲得真好"
LLM 误识别为：ask 这个视频讲得真好
```

**对策**：
- Prompt 里加"判断是否是有效需求"
- 对于纯评论性输入，输出 `error: 无法理解意图`

### 风险 3：向后兼容性

如果用户已经习惯传统命令，突然改成自然语言会不会不适应？

**对策**：
- 传统命令继续支持（检测到 `run` / `ask` 开头，跳过 LLM）
- 文档同时列出两种用法

---

## 替代方案

### 方案 A：不做自然语言解析，保持传统 CLI

优点：
- 实现简单（0 行额外代码）
- 无 LLM 调用成本
- 解析不会出错

缺点：
- 用户体验差（需要记命令）
- 不符合 Agent 定位
- 未来扩展受限（无法加多轮对话、语音输入）

### 方案 B：只在问答模块加自然语言，其他保持传统

`framelearn run <URL>` 保持传统，但 `framelearn` 进入问答模式后支持自然语言。

优点：
- 折中方案，问答体验好

缺点：
- 体验不一致（处理视频用命令，问答用自然语言）
- 仍需记住 `run` 命令

---

## 决策

**推荐：实现完整的自然语言入口**

理由：
1. 成本极低（开发 1-2 天，运行成本可忽略）
2. 价值高（用户体验质的提升）
3. 风险可控（传统命令向后兼容）
4. 符合 FrameLearn 的 Agent 定位

这是"锦上添花"中性价比最高的一个功能。
