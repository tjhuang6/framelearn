# FrameLearn：视频转顺序图文讲稿的 Agent 与模型选型

> 更新目标：本文档以 FrameLearn 当前项目实现和最新需求为准。
>
> 核心需求不是“把字幕提炼成知识点、重排成课程结构”，而是：
>
> **保留老师讲解的原始顺序，结合视频画面中的关键帧，生成一份不看原视频也能阅读和理解的 Markdown 语音讲稿。**

## 1. 需求重新定义

FrameLearn 的目标产物不是传统意义上的“课程摘要”或“知识库”，而是“视频的可阅读替身”或“顺序图文讲稿”：

- 字幕决定文字内容的时间顺序；
- 关键帧补充观众在视频中本来能看到的画面；
- 大模型负责把口语转成自然、完整、可读的书面讲稿；
- 不能因为追求教材结构而打乱老师的讲解顺序；
- 不能擅自总结、删掉重要的过程、补充视频中没有说过的知识；
- 图片应插入到它在视频时间轴上对应的位置；
- 最终用户只阅读 Markdown，也能大致获得“看视频”的体验。

因此更准确的产品定位是：

```text
视频 → 带时间戳的 ASR 字幕
    → 画面变化检测与关键帧
    → 字幕和关键帧按时间轴对齐
    → 按原始顺序生成图文语音稿 Markdown
```

如果以后增加教材章节、练习题、知识图谱或 RAG 问答，那是后续能力，不应成为当前 MVP 的硬性目标。

## 2. 当前项目的实际基础

FrameLearn 当前已经具备一条比较清晰的处理链：

```text
VideoPipeline
  ├── FFmpegHelper：提取音轨、场景检测、定时保底抽帧
  ├── ASRAdapter：调用 Qwen ASR / DashScope ASR
  ├── SubtitleCleaner：清理 ASR 噪声并保留时间轴语义
  ├── KeyframeDeduplicator：感知哈希去重
  └── DocumentGenerator：将字幕和关键帧生成 Markdown
```

当前配置中，ASR 已经使用 Qwen 的文件转写模型：

```toml
[asr]
provider = "dashscope"
model = "qwen-audio-3.0-asr-flash-filetrans"
language_hints = ["zh", "en"]
timestamp_alignment_enabled = true
```

项目还支持两种模型连接方式：

```toml
[runtime]
text_mode = "appserver"
vision_mode = "appserver"
```

以及直接调用 OpenAI-compatible API 的 `api` 模式。模型选型和运行模式是两件事：

- `appserver` / `api`：决定怎样调用模型；
- `vision_model` / `text_model`：决定调用哪个模型。

## 3. 推荐的处理流程

### 3.1 预处理：尽量使用本地确定性工具

```text
视频
 ├── ffprobe：获取时长、帧率、音视频起始偏移
 ├── ffmpeg：提取音轨
 ├── Qwen ASR：生成带句级/词级时间戳的字幕
 ├── ffmpeg scene 检测：发现明显画面切换
 ├── 固定间隔抽帧：作为静态画面保底
 └── pHash：删除近似重复帧
```

建议每一张关键帧都保存：

```json
{
  "path": "src/frame_001.jpg",
  "timestamp_seconds": 83.5,
  "source": "scene_change"
}
```

关键帧没有时间戳就无法可靠地插入到对应讲稿位置。FrameLearn 的内部时间单位建议使用整数毫秒，显示时再转换为 `HH:MM:SS.mmm`。

### 3.2 时间轴对齐

不要把“完整字幕”和“无时间信息的图片列表”一起交给模型让它猜。应该在程序中先完成粗对齐：

```text
关键帧时间 83.5 秒
    ↓
找到 81～86 秒附近的字幕片段
    ↓
把该帧挂到这段字幕之后或对应句子之后
    ↓
交给模型做画面说明和 Markdown 排版
```

每个处理片段建议包含：

```json
{
  "start": 60.0,
  "end": 120.0,
  "transcript": [
    {"start": 60.2, "end": 66.8, "text": "现在我们来配置数据库。"}
  ],
  "frames": [
    {"timestamp": 83.5, "path": "src/frame_001.jpg"}
  ]
}
```

### 3.3 生成：严格保持字幕顺序

模型的核心提示词应明确要求：

1. 按字幕时间戳从前到后生成；
2. 不进行知识点重排；
3. 不把后面才出现的内容提前；
4. 不把多个相距很远的片段合并；
5. 可以删除明显口头填充词、重复口误和无信息寒暄；
6. 必须保留老师的解释过程、例子、操作顺序和结论；
7. 看不清图片或听不清字幕时标注不确定，不要猜测；
8. 在关键帧对应的时间位置插入图片；
9. 输出合法 Markdown，不输出分析过程。

示例输出：

```markdown
# 视频标题

> 这是根据视频语音和画面按时间顺序整理的图文讲稿。

## 00:00:00

老师首先介绍本节课要完成的目标……

## 00:01:24

接下来打开项目配置文件，修改数据库连接地址。

![项目配置页面](src/frame_001.jpg)

## 00:02:10

修改完成后运行下面的命令。终端中出现启动成功的信息……

![启动成功的终端输出](src/frame_002.jpg)
```

## 4. 关键帧如何选择

不建议把视频逐帧发送给视觉模型。应采用“本地筛选为主、模型理解为辅”的方案。

### 第一层：本地抽帧

保留两类候选帧：

```text
1. scene change：检测到明显画面变化时抽帧
2. fallback interval：固定间隔保底抽帧
```

当前项目已有 `scene_threshold`、`fallback_interval` 和 `max_keyframes` 配置。建议初始值：

```toml
[video]
scene_threshold = 0.25
fallback_interval = 15
max_keyframes = 100
```

实际值应按视频类型调整：

- PPT 讲解：10～20 秒保底一帧；
- 代码演示：3～8 秒保底一帧；
- 软件操作：2～5 秒保底一帧；
- 静态讲解：15～30 秒保底一帧；
- 场景变化帧作为额外候选，不替代保底帧。

### 第二层：pHash 去重

同一张 PPT 可能持续几分钟。对于相似帧只保留一个代表帧，但不要丢失时间轴信息：代表帧应保存它第一次出现的时间，必要时也保存最后一次出现时间。

### 第三层：视觉模型只做画面理解

视觉模型的职责是描述已经选出的图片：

- 这是 PPT、代码、终端、板书还是摄像头画面；
- 图片中有哪些可见文字、代码、公式或步骤；
- 这张图片相对于附近字幕提供了什么额外信息；
- 图片是否应该插入 Markdown；
- 图片说明应该怎么写。

视觉模型不需要重新决定整门课程的结构，更不需要把字幕改造成知识点列表。

## 5. 模型选择结论

### 5.1 最推荐的默认方案：Qwen3-VL-32B-Instruct

如果通过硅基流动调用，当前模型中心显示：

```text
模型：Qwen/Qwen3-VL-32B-Instruct
输入：￥1 / M Tokens
输出：￥4 / M Tokens
场景：多模态理解 / 识别
```

它适合作为 FrameLearn 的主视觉模型，原因是：

- 中文场景匹配；
- 适合 PPT、代码、截图、图表和页面布局理解；
- 32B 相比小模型更适合识别教学画面中的细节；
- 价格仍明显低于许多旗舰视觉模型；
- 硅基流动提供 OpenAI-compatible API，接入项目现有 `ProviderAdapter` 的成本较低。

推荐用途：

```text
Qwen3-VL-32B
  → 分析候选关键帧
  → 识别 PPT/代码/终端/板书
  → 读取图片中的关键内容
  → 生成图片说明
  → 按时间轴将字幕和图片组织成顺序 Markdown
```

### 5.2 成本优先方案：Qwen3-VL-8B-Instruct

硅基流动当前模型中心显示：

```text
模型：Qwen/Qwen3-VL-8B-Instruct
输入：￥0.5 / M Tokens
输出：￥2 / M Tokens
场景：多模态理解 / 识别
```

适合：

- 关键帧分类；
- 重复画面二次判断；
- 简单 OCR 和图片描述；
- 第一版大规模批处理；
- 先跑通整个产品流程。

不建议一开始就让 8B 模型负责所有复杂代码、公式和密集 PPT 的最终识别。更适合采用级联：

```text
Qwen3-VL-8B：处理大多数普通帧
Qwen3-VL-32B：只复核代码、公式、复杂图表和低置信度帧
```

这是我认为目前在成本和效果之间最实用的方案。

### 5.3 质量优先或复核方案：Qwen3-VL-32B + 更强模型抽样复核

不要把所有图片都交给高价模型。可以把以下内容交给更强模型复核：

- 代码文字无法确认；
- 公式或图表识别失败；
- 字幕说“如图所示”，但画面说明为空；
- 视觉内容和字幕内容明显冲突；
- 生成 Markdown 后发现某个时间段缺少图片；
- 模型输出置信度低。

当前不建议直接把 Qwen3-VL-235B 当作默认全量模型：视觉任务的成本和吞吐压力更高，而 FrameLearn 的主要信息已经由 Qwen ASR 按顺序提供。高阶视觉模型应作为少量复核模型，而不是每帧调用。

### 5.4 硅基流动上的备选：GLM-4.5V

硅基流动当前模型中心显示：

```text
模型：zai-org/GLM-4.5V
输入：￥1 / M Tokens
输出：￥6 / M Tokens
场景：旗舰全能、多模态理解 / 识别
```

它可以作为对照测试模型，尤其适合比较：

- 中文图片说明；
- PPT 和图表理解；
- 代码截图识别；
- 复杂画面与字幕的对应关系。

但从价格看，GLM-4.5V 的输出价格高于 Qwen3-VL-32B，因此不建议作为默认全量模型。先使用 5～10 个真实视频片段做 A/B 测试，再决定是否保留。

### 5.5 DeepSeek 不应作为当前视觉默认模型

项目当前 `settings.toml` 里有：

```toml
vision_provider = "deepseek"
vision_model = "deepseek-reasoner"
```

但这不能直接证明当前模型适合图像输入。FrameLearn 的视觉任务必须确认 provider 的模型能力元数据和实际 API 测试结果。DeepSeek 可以继续作为文本任务的候选，但不应在没有验证视觉输入能力的情况下作为默认视觉模型。

## 6. 推荐的模型分工

当前已有 Qwen ASR，因此建议拆成以下角色：

| 任务 | 推荐模型/工具 | 原因 |
|---|---|---|
| 音频转写 | Qwen ASR（现有 DashScope 配置） | 已有集成，适合长音频和时间戳 |
| 场景检测 | FFmpeg | 本地、免费、稳定 |
| 图片去重 | pHash/imagehash | 本地、免费 |
| 普通关键帧理解 | Qwen3-VL-8B | 便宜 |
| 复杂关键帧理解 | Qwen3-VL-32B | 效果和成本平衡 |
| 视觉复核 | Qwen3-VL-32B 或 GLM-4.5V | 只处理异常帧 |
| 顺序讲稿生成 | Qwen 文本模型，或同一个 Qwen3-VL-32B | 只保留字幕顺序，不需要视觉模型重排知识 |
| 结构/格式检查 | 便宜文本模型 + Python 校验 | 检查时间戳、图片路径和 Markdown |

### 推荐的第一版配置

```text
ASR：Qwen ASR（当前 DashScope 配置）
视觉：Qwen3-VL-32B-Instruct
文本：硅基流动上的低价强文本模型，先测试 DeepSeek-V3.2 或 Qwen 当前文本模型
抽帧：FFmpeg + pHash
调用方式：API 直连优先
```

### 推荐的低成本配置

```text
ASR：Qwen ASR
视觉：Qwen3-VL-8B-Instruct
文本：DeepSeek-V3.2 或同等级低价文本模型
异常帧复核：Qwen3-VL-32B
```

硅基流动当前页面显示 DeepSeek-V3.2 的输入价格为 ￥2/M Tokens、输出价格为 ￥3/M Tokens。它适合做顺序文本改写和 Markdown 生成，但仍应以实际 API 能力和项目测试为准。

## 7. 为什么不建议直接把完整视频交给一个视频模型

你的输入已经被拆成：

```text
Qwen ASR → 有时间戳的语音内容
关键帧 → 画面内容
```

这是更便宜、更可控的方案。直接使用“视频理解模型”并不一定更好：

- 原始视频体积大，上传和等待时间长；
- 模型未必能提供稳定的逐句时间对齐；
- 视频中大量连续帧是重复信息；
- 你最终只需要在讲稿中插入少量代表图片；
- ASR 对中文长音频和时间戳通常更适合专门处理。

只有在以下场景，才值得测试原生视频输入模型：

- 需要理解连续动作，而不是静态 PPT；
- 需要判断鼠标操作的完整过程；
- 需要观察实验、手写推导或体育动作；
- 关键事件发生得非常快，抽帧可能遗漏。

对于普通编程教学、PPT 教学和单人讲解，当前的“ASR + 关键帧”方案更经济。

## 8. 这是 Agent 还是 Workflow

当前 FrameLearn 的主体仍然是一个多模态 Workflow：

```text
提取音频 → Qwen ASR → 抽帧 → 去重 → LLM 生成 Markdown
```

调用一次视觉/文本模型，并不会自动让系统成为 Agent。

FrameLearn 可以被称为 Agent，是因为项目架构已经规划了自然语言入口、工具调用、规划、内容分析、问答和质量检查。但要让“视频转顺序图文讲稿”真正具备 Agent 特征，需要让模型根据中间结果做有限的决策，例如：

```text
1. 发现关键帧太少 → 调低 scene_threshold 或缩短 fallback_interval
2. 发现某段字幕提到“如图”但没有对应图片 → 补抽附近帧
3. 发现图片文字不清楚 → 请求更高分辨率帧或升级到 32B 模型
4. 发现字幕和画面描述冲突 → 标记该时间段并重新复核
5. 发现 Markdown 缺失图片或时间戳 → 自动修复后再输出
```

建议不要一开始让多个大模型自由对话。更可靠的产品结构是：

```text
确定性的媒体预处理
+
一个负责决策和重试的 Orchestrator
+
Qwen-VL 视觉工具
+
顺序讲稿生成器
+
Python 格式和时间轴校验
```

这样既保留 Agent 的自适应能力，也不会因为无约束循环显著增加成本。

## 9. 建议的成本控制策略

```text
1. Qwen ASR 只做一次，并缓存 transcript.json
2. FFmpeg、pHash 和时间轴对齐尽量本地完成
3. 不把重复关键帧发送给视觉模型
4. 8B 处理普通帧，32B 处理高价值或异常帧
5. 文本讲稿生成只使用对应时间段的字幕和图片说明
6. 长视频按 30～120 秒分段，不发送整部视频的全部内容
7. 只对低置信度片段重试
8. 用 Python 校验 Markdown，而不是用大模型反复检查格式
```

推荐的成本分布：

```text
本地算法：大部分帧筛选
Qwen3-VL-8B：普通帧理解
Qwen3-VL-32B：重要帧和异常帧
低价文本模型：按顺序生成讲稿
```

## 10. 需要修改的生成器行为

当前 `DocumentGenerator` 的 prompt 仍然偏向“正式教材”：

- 自然分章节；
- 每个概念完整引入、解释、示例、小结；
- 组织成知识点；
- 可能改变原始讲解节奏。

这与当前需求不完全一致。建议新增一个模式，例如：

```python
DocMode = Literal["notes", "textbook", "visual_script"]
```

`visual_script` 模式应该：

- 按字幕时间顺序生成；
- 不做知识点重排；
- 不强制生成章节总结；
- 保留老师的讲解过程和例子；
- 在对应时间点插入关键帧；
- 删除少量明显口水词，但不大幅改写；
- 输出图片的时间戳和相对路径；
- 对看不清的内容输出 `[画面无法确认]`，禁止猜测。

另外，当前生成器只把前 20 张关键帧写进 `frames_description`，而 API 分支也只发送前 20 张图片。长视频应改为按时间片段调用，而不是简单截断前 20 张，否则后半段视频会丢失。

## 11. 评测方法：先用真实片段做 A/B 测试

建议准备 5～10 个真实片段，覆盖：

- PPT 讲解；
- 代码编辑器；
- 终端命令和输出；
- 公式或图表；
- 纯老师讲话；
- 画面变化很少但字幕内容持续变化的片段。

比较以下指标：

1. 关键帧是否插入了正确时间位置；
2. 图片中文字和代码是否识别正确；
3. 是否严格保持老师讲解顺序；
4. 是否遗漏字幕中的重要过程；
5. 是否出现模型凭空补充；
6. Markdown 中图片路径是否全部有效；
7. 单个视频的模型费用；
8. 总处理时间和失败重试次数。

推荐实际测试的模型组合：

```text
A：Qwen3-VL-8B + 低价文本模型
B：Qwen3-VL-32B + 低价文本模型
C：Qwen3-VL-32B + GLM-4.5V 仅异常帧复核
```

不要只看模型排行榜。对 FrameLearn 来说，决定最终体验的因素通常按以下顺序排列：

```text
时间戳是否准确
> 关键帧是否选对
> 是否保持原始顺序
> 图片文字/代码是否正确
> 书面表达是否自然
> 模型价格
```

## 12. 最终建议

我的实际建议是：

```text
第一步：继续使用现有 Qwen ASR，不更换已经稳定的转写链路。

第二步：把当前目标从“教材生成”改为“visual_script / 顺序图文讲稿”。

第三步：优先通过硅基流动 API 测试 Qwen/Qwen3-VL-32B-Instruct。

第四步：如果成本需要进一步下降，改用 Qwen/Qwen3-VL-8B-Instruct，
        只把复杂帧升级到 32B。

第五步：使用低价文本模型按字幕顺序生成 Markdown，
        不让模型重排知识和章节。

第六步：增加低置信度重试、缺图检查、时间戳检查，
        这时 FrameLearn 才真正具备 Agent 的自适应部分。
```

当前最推荐的默认组合：

```text
Qwen ASR
+ FFmpeg / pHash
```
