不过我发现几个当前会直接影响3小时视频的关键问题。

1. VideoPipeline 强制使用硅基流动

video_pipeline.py 第77行：

python
asr = ASRAdapter(provider="siliconflow")


这会忽略 settings.toml 中的：

toml
[asr]
provider = "dashscope"


即使你修改配置，实际仍会调用 SenseVoice。

应该改成：

python
asr = ASRAdapter()


让适配器读取配置。

2. 当前默认模型仍然是 SenseVoiceSmall

settings.toml 当前是：

toml
provider = "siliconflow"
model = "FunAudioLLM/SenseVoiceSmall"


而 SenseVoice 后端不返回时间戳：

python
has_timestamps=False
srt=None


这会导致关键帧无法与讲师当时讲解的内容准确对应。

如果使用现有 DashScope 实现，应改为：

toml
[asr]
provider = "dashscope"
model = "paraformer-v2"


3. 最严重：字幕只取前12000个字符

doc_generator.py 第114行：

python
subtitle=subtitle[:12000]


3小时教学音频的绝大部分内容会被直接截掉。最终教材可能只覆盖视频前面一小部分。

这不是简单提高字符上限就能彻底解决，正确方案应该是：

text
完整字幕
→ 按时间/主题切成章节
→ 每章分别生成Markdown
→ 最后统一合并、去重和生成目录


推荐每个教材生成单元覆盖：

text
10～20分钟视频内容


而不是把3小时字幕一次性交给模型。

4. 关键帧只使用前20张

doc_generator.py：

python
for i, frame in enumerate(keyframes[:20])


但是项目允许最多100张关键帧。这意味着后面80张帧不会进入生成提示。

另外，提示词当前只传入：

text
关键帧 1: frame_001.jpg


并没有可靠地把图片本身及其对应时间戳绑定给模型。对视频教材而言，真正应该传递的是：

text
时间：00:18:32
字幕：现在我们创建一个卷积层……
图片：frame_014.jpg


否则模型不知道截图属于课程的哪一段。

为什么不建议只用 Omni 一步完成

qwen3.5-omni-flash 可以直接听3小时音频并输出字幕、摘要和教材，但作为生产流水线仍有这些风险：

- 时间戳是生成文本，不是专业 ASR 的结构化词级时间戳
- 官方标明不支持严格结构化输出
- 长输出可能被截断
- 某次失败需要重新处理大量内容
- 很难准确追踪某张截图对应哪句讲解
- 无法轻松校正单个章节
- 成本高于 Paraformer
- 教材生成结果不容易审计和回溯

但是 Omni 非常适合每章10～20分钟的“音频 + 关键帧 + ASR字幕”联合理解。这正是它在 FrameLearn 里的最佳位置。

每章先构造一个中间文件：

然后让模型逐章生成：

最后合并：

→ 去除章节间重复
→ 生成目录
→ index.md


这样3小时视频也不会丢内容。
