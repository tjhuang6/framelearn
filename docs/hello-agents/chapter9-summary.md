# 第九章《上下文工程》学习笔记

## 概述

本章引入"上下文工程（Context Engineering）"这个比提示工程更宏观的概念，并在 HelloAgents 框架中实现了三个新组件：**ContextBuilder**（GSSC 流水线）、**NoteTool**（结构化笔记）、**TerminalTool**（终端文件操作）。这三者共同解决一个核心问题：**在长时程任务中，如何持续、系统地为模型维护一个"高质量、有限大小"的上下文窗口**。

## 什么是上下文工程，为什么它比提示工程更重要

**提示工程**关注的是"怎么写指令能让模型表现更好"，是一次性的文本设计问题。**上下文工程**关注的是"在每一次模型调用前，往上下文窗口里放什么"，是一个持续运行的工程问题。

两者的区别在时间维度上最明显：提示工程适合单轮或少轮场景，而一个运行数十步的 Agent 会不断产生新信息（工具输出、中间结论、对话历史……），这些信息全塞进去会超出窗口，全丢掉会失去连续性。上下文工程的任务就是在这两个极端之间做工程化的取舍。

## 上下文腐蚀：为什么不能无限堆 Token

一个反直觉的现象：即使模型支持 100K+ 的上下文窗口，往里面堆越多的 token，模型从中准确提取信息的能力反而会下降。这叫**上下文腐蚀（context rot）**。

原因在于 Transformer 的注意力机制：每个 token 要与所有其他 token 建立关联，上下文变长时注意力被"拉薄"，模型对每个 token 的关注度下降。训练数据中短序列比长序列多，模型对长上下文的经验本来就少。

结论：**上下文是有限的注意力预算，每个 token 都有成本**。上下文工程的目标是"用尽可能少但信息密度高的 token，最大化获得期望输出的概率"。

## 有效上下文的三个关键组件

**系统提示**：语义清晰、分区组织（建议用 XML 或 Markdown 分隔不同区块，如 `[Role]`、`[Task]`、`[Instructions]`）。两个常见误区：一是写了复杂的 if-else 逻辑（脆、难维护），二是太空泛、没有具体信号。追求"能完整描述期望行为的最小必要信息集"。

**工具**：职责单一、边界清晰。工具描述不清会让模型不知道该调哪个。"如果人类工程师都说不准用哪个工具，别指望 Agent 做得更好"——保持最小可行工具集（MVTS）。

**Few-shot 示例**：挑选多样且典型的示例，而不是罗列所有边界条件。好的示例直接画像期望行为，比详细的文字描述更有效。

## JIT 上下文与渐进式披露

传统做法是在 Agent 启动时一次性加载所有可能相关的数据（embedding 预检索）。更现代的做法是 **JIT（Just-in-time）上下文**：只预存文件路径、存储 key、URL 等轻量引用，在运行时通过工具按需加载。

这和人类认知模式一致：我们不会背下所有信息，而是记住"去哪里找"。JIT 上下文带来的另一个效果是**渐进式披露**：每一步工具调用都返回新信息，这些信息又指导下一步决策——文件名暗示用途，时间戳暗示时效，目录结构暗示复杂度。

代价是运行时探索比预计算慢，且需要模型有足够的"主见"来决定探索方向，否则会在死胡同上浪费大量 token。实践中混合策略更有效：预加载少量高价值上下文（如 README），同时提供 `grep`、`ls` 等工具按需探索。

## 长时程任务的三种应对策略

**压缩整合（Compaction）**：上下文快满时，让模型对历史做高保真摘要，丢弃重复的工具输出和噪声，保留架构决策和关键结论，用摘要 + 少量高相关工件重启一个新上下文窗口。

**结构化笔记（NoteTool）**：以固定频率把关键信息写入上下文外的持久化存储（文件、数据库），后续按需拉回。适合有里程碑的迭代式任务，能用极低的上下文开销维持跨数十步的状态一致性。

**子代理架构**：主代理负责规划和综合，多个专长子代理各自在干净的上下文中完成子任务，最后只回传凝练摘要（通常 1000–2000 tokens）。适合需要并行探索的复杂研究任务。

选择依据：需要长对话连续性 → 压缩整合；有里程碑 → 结构化笔记；需要并行探索 → 子代理架构。

## ContextBuilder：GSSC 流水线

ContextBuilder 把上下文构建抽象为四个阶段，对外提供单一的 `build()` 接口：

**Gather（收集）**：从记忆系统、RAG 知识库、对话历史、系统指令等多个来源收集候选信息，统一封装为 `ContextPacket` 对象（包含 content、timestamp、token_count、relevance_score、metadata）。

**Select（选择）**：给每个 ContextPacket 打综合分，然后贪心填充：

```
combined_score = relevance_weight × 相关性 + recency_weight × 新近性
```

相关性用 Jaccard 关键词重叠（生产环境可换向量相似度），新近性用指数衰减（24 小时内高分，之后逐渐衰减）。按分数从高到低填充，直到触碰 token 预算上限。

**Structure（结构化）**：把选中的信息按类型组织为固定模板：

```
[Role & Policies]   ← 系统指令
[Task]              ← 当前任务
[State]             ← 当前状态
[Evidence]          ← RAG 检索到的证据
[Context]           ← 对话历史和记忆
[Output]            ← 期望输出格式
```

**Compress（压缩）**：如果结构化后的文本仍超出 token 预算，调用 LLM 对低优先级内容做智能摘要，作为兜底机制。

```python
agent = ContextAwareAgent(
    name="数据分析顾问",
    llm=HelloAgentsLLM(),
    system_prompt="你是一位资深的 Python 数据工程顾问。",
    user_id="user123",
    knowledge_base_path="./data_science_kb"
)

response = agent.run("如何优化 Pandas 的内存占用？")
```

ContextBuilder 在 `run()` 内部自动完成 GSSC 四步，Agent 代码无感知。

## NoteTool：持久化结构化笔记

NoteTool 解决的问题是：Agent 跑了几十步之后，重要结论、待办事项、阻塞问题不能只靠上下文携带——它们需要写到上下文外的持久存储里，随时可以按需读回。

每条笔记存储为一个带 YAML 元数据头的 Markdown 文件：

```markdown
---
id: note_20240119_160000_3
title: 重构项目 - 第一阶段
type: task_state
tags: [refactoring, phase1]
created_at: 2024-01-19T16:00:00
---

## 完成情况
已完成数据模型层的重构，测试覆盖率达到 85%。

## 下一步
重构业务逻辑层
```

笔记类型（`note_type`）有 `task_state`、`conclusion`、`blocker`、`action`、`reference` 等，便于按类型过滤检索。NoteTool 与 ContextBuilder 集成时，检索到的笔记会被转换为 ContextPacket，以较高相关性分（0.75）参与 Select 阶段竞争。

## TerminalTool：受限的文件系统操作

TerminalTool 让 Agent 能够像人类开发者一样在文件系统中探索——查看目录结构、读取文件内容、搜索代码模式。设计上的核心问题是：给 Agent 执行 shell 命令的能力，如何不让它做危险的事。

四层安全机制：
1. **命令白名单**：只允许 `cat`、`ls`、`grep`、`find`、`head`、`wc` 等只读类命令，`rm`、`chmod`、`curl` 等危险命令直接拒绝
2. **工作目录沙箱**：只能访问初始化时指定的 `workspace` 目录及其子目录，`cd ../../etc` 这类路径逃逸会被拦截
3. **超时控制**：每条命令有执行时间上限（默认 30 秒），防止无限循环
4. **输出大小限制**：默认 10MB，超出自动截断

典型工作模式是"探索式导航"——先 `ls`，再 `cd src`，再 `grep -r 'def process'`，再 `cat user_service.py`，逐步建立对代码库的理解。TerminalTool 发现的信息可以通过 MemoryTool 存入语义记忆，重要发现可以通过 NoteTool 记录为结构化笔记。

## 与 FrameLearn 的关联

FrameLearn 的规划 Agent 和工具执行器天然涉及长时程任务，本章的所有组件都有直接对应。

**GSSC Pipeline（ContextBuilder）是 FrameLearn 处理长视频的核心工具**。FrameLearn 在处理长视频时已经使用 ContextBuilder，对应关系非常直接：Gather 阶段收集转录文本片段、OCR 结果、关键帧描述；Select 阶段按相关性和时间近因性筛选有效信息；Structure 阶段组装成分析 prompt；Compress 阶段在上下文超限时对已处理的视频段做摘要。这正是 GSSC Pipeline（即代码里的 ContextBuilder）设计的典型场景。

**NoteTool 对应规划 Agent 的任务状态管理**。规划 Agent 分析视频结构时，会产生大纲草稿、章节划分方案、待确认问题等中间产物。用 NoteTool 以 `task_state` 类型持久化这些状态，在后续各模块（工具执行器、内容分析器、文档生成器）运行时按需读回，可以在任何一步中断后从笔记恢复进度，避免重跑整个流水线。

**TerminalTool 对应工具执行器中的文件操作**。yt-dlp 下载、ffmpeg 截帧、Whisper 转录等工具会生成大量临时文件。TerminalTool 的沙箱模式可以让 Agent 安全地用 `ls`、`find`、`wc -l` 等命令检查输出文件是否完整，而不用担心意外破坏文件系统。

**渐进式披露思路对应内容分析器的关键帧筛选策略**。内容分析器不应该一次性把所有帧都加载进上下文，而是按时间顺序渐进地"看"视频——先看关键帧，发现有价值的内容再深挖，这和 JIT 上下文的思路完全一致。

**子代理架构对应 FrameLearn 的多模块并行化方向**。如果规划 Agent 将视频切分为多个章节后，可以让多个子代理分别处理各章节（各自独立的上下文），最后汇总结果——这是本章子代理架构思路在 FrameLearn 中的直接应用。
